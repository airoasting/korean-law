# 판정 규칙

정본은 엔진 `mcp/src/verdict.ts`의 `GATE_STATUS`·`computeVerdict`와 `scripts/kl.py`의 `STATUS`·`compute_verdict`다. 둘은 같은 표다. 이 문서는 그 규칙을 사람이 읽도록 풀어 쓴 것이다. 셋이 어긋나면 코드를 기준으로 하고, 이 문서를 고친다.

## 상태

### PASS 등급

| 상태 | 뜻 | 엔진이 내리는 조건 |
|---|---|---|
| `OK` | 실존하고 기준일에 시행 중이다 | 정식 법령명으로 찾았고, 기준일 본문에 조문(항·호)이 있고, 삭제되지 않았고, 인용 제목이 맞고, 시행 예정 개정이 없다. 판례는 실존·선고일 일치·생사 확인 통과 |
| `OK_ALIAS` | 약칭이지만 정식 법령에서 확인했다 | 법제처 공식 약칭 또는 통칭 사전으로 정식 명칭을 찾은 뒤 위 조건 통과 |

### FAIL 등급 (하나라도 있으면 반려)

| 상태 | 뜻 | 엔진이 내리는 조건 |
|---|---|---|
| `FAIL_NOT_FOUND` | 법령은 있지만 그 조문(항·호)이 없다 | 기준일 본문과 최종 본문 모두에 없다. 항·호 구조를 읽지 못하면 FAIL 대신 `WARN_UNCHECKED` |
| `FAIL_MISMATCH` | 인용한 조문 제목이 실제 제목과 다르다 | 정규화한 두 제목이 같지도, 한쪽이 다른 쪽을 포함하지도 않는다 |
| `FAIL_LAW_NOT_FOUND` | 그런 법령이 없다 | 현행·연혁·폐지 어디에서도 정확히 같은 이름이 없고, 이름이 정식 명칭 꼴이다 (약칭 꼴이면 `WARN_ALIAS_UNREGISTERED`) |
| `FAIL_IMPOSSIBLE_CASE` | 존재할 수 없는 사건번호다 | 사건번호의 연도가 확인일보다 미래다 |
| `FAIL_CASE_MISMATCH` | 사건번호는 실존하지만 본문에 적힌 선고일이 실제와 다르다 (다른 판례를 가리킨다) | 본문에서 사건번호 바로 앞 날짜와 실제 선고일을 대조 |
| `FAIL_REPEALED` | 폐지된 법령을 현행처럼 인용했다 | 법령이 폐지됐고 본문에 '구' 또는 '(구)' 표기가 없다 |
| `FAIL_DELETED` | 조문이 삭제됐다 | 기준일 본문의 그 조문이 '삭제 <날짜>' 한 줄이다. 삭제가 아직 시행 전이면 `WARN_PENDING_CHANGE` |
| `FAIL_OVERRULED` | 판례가 후속 판결로 변경·폐기됐다 | 후속 판결 본문에서 대상 사건번호 주변(앞뒤 350자)에 변경·폐기 문구가 있다 |

### WARN 등급 (본문에 반영해야 통과)

| 상태 | 뜻 | 엔진이 내리는 조건 |
|---|---|---|
| `WARN_RENAMED` | 옛 법령명이다 | 연혁에 그 이름이 있고 지금 이름이 다르다 |
| `WARN_TITLE_DIFF` | 인용 제목이 실제 제목과 표기가 다르다 (의미는 같다고 볼 수 있다) | 느슨한 대조는 통과했지만 엄격한 대조('등' 꼬리, 가운뎃점·'및', 삼·3 차이만 같게 본다)에서 다르다 |
| `WARN_PENDING_CHANGE` | 기준일에는 유효하지만 시행 예정 개정·삭제가 있다 | 기준일 본문과 최종 공포본 본문이 다르다 |
| `WARN_NOT_YET_EFFECTIVE` | 공포됐으나 아직 시행 전인 신설 조문·항·호다 | 기준일 본문에는 없고 최종 공포본에만 있다 |
| `WARN_REPEALED_HISTORICAL` | '구 ○○법'으로 일부러 구법을 인용했다 | 폐지 법령 + 본문에 '구' 또는 '(구)' |
| `WARN_CASE_UNVERIFIED` | 판례가 검색되지 않는다. 부존재로 단정하지 않는다 | 법제처 판례·헌재 결정 어디에도 같은 사건번호가 없다 |
| `WARN_CITE_UNCERTAIN` | 판례 생사를 확정하지 못했다 | 후속 판결을 다 읽지 못했거나, 읽었지만 대상 사건번호를 찾지 못했다 |
| `WARN_LAW_UNRESOLVED` | 법령명을 특정하지 못했다 | 수동 기록용 |
| `WARN_ALIAS_UNREGISTERED` | 약칭 꼴 이름이 법제처 약칭 사전에 없다. 실존 법령일 수 있다 | 정식 명칭을 찾지 못했고 이름이 공백 없는 짧은 '…법' 꼴이다 (`build`도 overrides의 `FAIL_LAW_NOT_FOUND`를 같은 조건에서 이것으로 낮춘다) |
| `WARN_UNCHECKED` | 검증하지 못했다 | 법령명이 생략된 조문(`needs_context`), 조회 실패, 항·호 구조 미확인 |

### SKIP 등급 (판정에서 제외)

| 상태 | 뜻 | 기록 조건 |
|---|---|---|
| `EXCLUDED` | 법령 인용이 아니라 문서 자체의 조항이다 (계약서 제12조 등) | 문맥 확인. 근거 문장이 `input.md`에 그대로 있어야 `build`가 받아들인다 |
| `REPLACED` | 법령명을 문맥으로 특정해 다른 항목으로 재검증했다 | 문맥 확인 후 재검증 묶음. `replaced_by` 항목과 조문 번호가 같아야 `build`가 받아들인다 |

## overrides 적용 규칙

- `parse`가 그 항목에 요구한 확인(`checks`, 현재는 `SCOPE_CHECK`뿐)만 판정에 반영한다. 요구하지 않은 확인 기록은 무시하고 `reasons`에 남긴다. 낡은 기록이 FAIL을 덮는 일을 막는다.
- 수동 추가 항목(`M*`)과 `check: "MANUAL"`은 예외다.
- 상태가 바뀌면 '고칠 곳' 안내도 새 상태의 안내로 바뀐다. `fix`를 직접 적으면 그것을 쓴다.

## 문서 판정

1. SKIP을 뺀 인용이 하나도 없으면 `NO_CITATIONS`다.
2. FAIL 등급이 하나라도 있으면 `FAIL`이다.
3. WARN 등급이 있거나 끝내지 않은 문맥 확인이 있으면 `PASS_WITH_WARNINGS`다.
4. 그 밖에는 `PASS`다.

FAIL 항목에 남은 문맥 확인은 미완료로 세지 않는다. 이미 반려 사유가 있기 때문이다.

## 설계 원칙

- **오탐 0이 검출률보다 먼저다.** 진짜 인용을 FAIL로 판정하는 일이 한 번이라도 생기면 사람들이 게이트를 믿지 않는다. 그래서 판례 미확인은 FAIL이 아니라 WARN이고, 구조를 읽지 못한 항·호도 FAIL이 아니라 WARN이다.
- **기준일 본문으로 대조한다.** 법제처 '현행' 본문(공포일 기준)에는 아직 시행 전인 개정이 섞여 있다. 그대로 대조하면 오늘 유효한 조문을 '삭제'로 판정한다 (근로기준법 제105조, 2026-10-04 확인). 엔진은 연혁에서 기준일에 시행 중이던 버전을 고르고, 최종 공포본과의 차이는 경고로 알린다.
- **확인하지 않은 것은 통과가 아니다.** 문맥 확인을 건너뛰면 PASS가 나오지 않는다.
- **근거는 원문이다.** 엔진은 법제처 응답 한 줄을, overrides는 원문 문장이나 도구 결과 한 줄을 그대로 남긴다.
- **약칭과 부존재를 섞지 않는다.** 공백 없는 짧은 약칭 꼴 이름을 찾지 못한 것은 사전의 한계일 수 있다. 정식 명칭처럼 생긴 이름을 찾지 못한 것만 FAIL이다.
- **제외는 원문으로 증명한다.** `EXCLUDED`는 FAIL을 숨기는 통로가 될 수 있다. 그래서 근거 문장이 원문에 실제로 있어야 하고, 검증표에 따로 드러낸다.

## 갱신 기준

- 시드 평가(`../evals/`)에서 오탐이나 놓침이 나오면, 먼저 시드로 재현하고, 그다음 규칙을 고치고, 이 문서를 고친다.
- 새 상태를 추가하면 `verdict.ts`, `kl.py`의 `STATUS`, 이 문서, `evidence-schema.md`를 함께 고친다.
