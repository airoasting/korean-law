# korean-law

AI가 쓴 한국 법률 문서의 조문·판례 인용을 **법제처 DB로 검증해 통과·반려를 판정하는** 스킬과 MCP 서버다. **Claude Code와 Codex** 양쪽에서 같은 스킬 폴더와 같은 MCP 서버로 동작한다. 설치는 [아래](#설치)에 도구별로 있다.

계약서 검토, 법률 의견서, 준비서면, 세무·내부통제 문서를 넣으면 인용 하나하나를 실존, 현행, 제목, 선고일, 판례 생사까지 대조한 **법률 근거 검증표**가 나온다. 의견을 내지 않고 사실만 판정한다.

> 영감: 법제처 Open API를 MCP로 묶은 [chrisryugj/korean-law-mcp](https://github.com/chrisryugj/korean-law-mcp)에서 아이디어를 얻었다.

## 왜 만들었나

요즘은 계약서 검토 메모나 법률 의견서 초안을 AI에게 맡기는 일이 많다. 문장은 그럴듯하다. 문제는 그 안에 적힌 "○○법 제△조", "대법원 ○○다○○ 판결"이 정말 맞는지를 법을 모르는 사람은 확인하기 어렵다는 점이다.

그래서 직접 시험해 봤다. AI(Claude)에게 15년 차 기업 변호사 역할을 주고 법무 문서 5편을 쓰게 한 뒤, 인용 81건을 하나씩 법제처 원문과 맞춰 봤다. 3건이 틀렸고, 5편 중 2편은 그대로 쓰면 안 되는 문서였다.

| 문서 | AI가 쓴 인용 | 실제 |
|---|---|---|
| 부당해고 준비서면 | 민사소송법 제272조(준비서면) | 제272조의 제목은 '변론의 집중과 준비'다 |
| 부당해고 준비서면 | 대법원 2003. 7. 22. 선고 2002두12052 (해고 판례로 인용) | 2005. 1. 28. 선고된 공정거래 사건이다 |
| 가지급금 세무 의견서 | 법인세법 시행령 제53조(업무무관 가지급금 등의 범위) | 제53조의 제목은 '업무무관자산등에 대한 지급이자의 손금불산입'이다 |

눈여겨볼 점은 세 건 모두 **번호 자체는 실제로 있다**는 것이다. 없는 번호를 지어낸 게 아니라, 있는 번호에 다른 내용을 붙였다. 그래서 흔히 쓰는 확인 방법으로는 잡히지 않는다.

- **AI에게 다시 물어보기**: 같은 AI가 같은 실수를 되풀이하거나, 물을 때마다 답이 달라진다.
- **인터넷 검색**: 오래 걸리고, 검색 결과가 지금 시행 중인 법인지 바뀌기 전 법인지 알기 어렵다.
- **번호가 있는지만 확인하기**: 위 세 건처럼 번호는 맞고 내용이 틀린 오류를 그대로 지나친다.

필요했던 것은 **법제처 원문을 기준으로, 내용까지, 매번 같은 기준으로, 몇 초 안에** 확인해 주는 도구였다. 하나 더 있다. AI가 쓴 초안을 여러 관점의 AI 비평가가 검토하는 작업 방식(Roasting)에서는, 근거가 틀린 법률 문서를 비평하는 것 자체가 시간 낭비다. 비평에 들어가기 전에 근거부터 걸러 내는 관문이 필요했다. korean-law는 그 두 가지를 위해 만들었다.

전체 시험 기록은 [evals/blackdocs/2026-10-04/FINDINGS.md](evals/blackdocs/2026-10-04/FINDINGS.md)에 있다.

## 무엇이 다른가

위의 문제를 풀려고 이렇게 만들었다.

**1. 번호만 맞춰 보지 않고 내용까지 본다.**
AI는 실제로 있는 조문 번호에 엉뚱한 제목을 붙이곤 한다. 예를 들어 '민사소송법 제272조(준비서면)'라고 썼지만, 실제 제272조의 제목은 '변론의 집중과 준비'다. korean-law는 조문 제목과 판결 날짜까지 법제처 원문과 맞춰 본다.

**2. 지금 시행 중인 법으로 확인한다.**
법은 자주 바뀐다. 법제처의 최신 본문에는 발표는 됐지만 아직 시행되지 않은 개정이 섞여 있어서, 그대로 비교하면 아직 유효한 조문을 '없어진 조문'으로 잘못 볼 수 있다. korean-law는 지금 실제로 시행 중인 본문으로 확인하고, 곧 바뀔 조문은 따로 알려 준다. 계약을 맺은 날처럼 과거의 특정 날짜를 기준으로도 확인할 수 있다.

**3. AI가 아니라 정해진 규칙이 판정한다.**
AI에게 "이 인용 맞아?"라고 물으면 물을 때마다 답이 달라질 수 있다. korean-law는 정해진 규칙으로 판정하므로 같은 문서는 언제 돌려도 같은 결과가 나온다. 판정마다 법제처에서 확인한 근거가 한 줄씩 붙는다.

**4. 멀쩡한 인용을 틀렸다고 하지 않는다.**
확실하지 않으면 '틀림'이 아니라 '확인 필요'로 표시한다. 예를 들어 법제처에 없는 판례를 가짜라고 단정하지 않는다. 하급심 판결은 법제처에 없을 수 있어서다. 인터넷 문제 등으로 확인을 못 했으면 '통과'로 넘기지 않고 '확인 못 함'으로 멈춘다. 시험용 문서 27개로 돌려 봤을 때, 진짜 인용 70건을 틀렸다고 한 경우는 한 번도 없었다.

**5. 문서를 넣으면 몇 초 만에 끝난다.**
'민법 750조', '같은 법 제3조'처럼 제각각인 표기나 법 이름을 생략한 조문도 알아서 읽는다. '본 계약서 제12조'처럼 계약서 자체의 조항은 법 조문이 아니라는 것도 구분한다. 문서 한 편에 보통 몇 초면 결과표가 나온다. Claude와 Codex 어디서든 같은 방법으로 쓸 수 있다.

## 예시

[examples/saas-contract-review/](examples/saas-contract-review/)에 SaaS 이용계약 검토 메모를 돌린 결과가 있다. 삭제된 조문(정보통신망법 제22조), 실존 사건번호에 다른 선고일, 원문과 다른 조문 제목, 지어낸 사건번호를 심어 두었고 네 건 모두 걸렸다. 진짜 인용 4건은 모두 통과했다.

```markdown
# 법률 근거 검증표

- 판정: **FAIL (반려)**
- 법령 인용 7건 (통과 4, 경고 1, 실패 1) · 판례 인용 2건 (통과 0, 경고 1, 실패 1)

## 반려 사유 (2)

| # | 인용 | 판정 | 근거 | 고칠 곳 |
|---|---|---|---|---|
| L6 | 정보통신망 이용촉진 및 정보보호 등에 관한 법률 제22조 | 삭제된 조문 | 제22조 삭제 <2020.2.4> | 삭제 사실을 반영해 고치거나 인용을 뺀다 |
| C1 | 2013다61381 | 사건번호는 실존하나 인용한 선고일과 다름 | 본문 선고일 20150326 ≠ 실제 20181030 (손해배상(기)) | 실제 판례를 찾아 사건번호와 선고일을 바로잡거나 인용을 뺀다 |
```

모든 판정에는 근거가 된 법제처 응답 한 줄이 붙는다. 기계가 읽는 `evidence.json`도 함께 나온다.

## 어떻게 작동하나

MCP 서버의 `verify_document`가 문서 한 편을 한 번에 검증한다. 문서당 수 초가 걸린다 (시드 27개 최대 4.3초).

| 단계 | 하는 일 |
|---|---|
| 1. 표기 정규화 | `민법 750조`, `§398`, `23조 1항`, `제390조 및 제750조`, `○○법(이하 '△△법')`을 `<법령명> 제N조` 꼴로 맞춘다 |
| 2. 인용 추출 | 조문(항·호·목 포함)과 사건번호를 뽑는다. `같은 법`, `동법 시행령`은 같은 문단의 앞 법령으로 푼다. `본 계약서 제12조`, `취업규칙 제5조` 같은 문서 자체 조항은 판정에서 뺀다 |
| 3. 법령 확인 | 약칭 사전(법제처 공식 약칭 2,542건)으로 정식 명칭을 찾고, 연혁에서 **기준일에 시행 중이던 버전**을 고른다. 옛 이름과 폐지 법령도 가린다 |
| 4. 조문 대조 | 기준일 본문에서 조문, 항, 호, 목, 삭제 여부, 인용한 제목을 대조한다. 공포됐지만 시행 전인 개정은 따로 경고한다 |
| 5. 판례 확인 | 사건번호 실존, 본문에 적힌 선고일, 헌재 결정을 확인한다. 실존 판례는 후속 판결을 찾아 전원합의체 본문에서 변경·폐기 문구를 확인한다 |
| 6. 판정 | 상태별 규칙으로 FAIL / INCOMPLETE / PASS_WITH_WARNINGS / PASS를 낸다 |

법령명이 생략된 조문(`…와 시행령 제53조`, `손해액은 제14조의2로`)은 앞 법령으로 추정해 검증한다. 같은 문장의 법령이면 그대로 믿고, 같은 문단의 법령이면 인용 제목이 실제 제목과 맞을 때만 믿는다. 그래도 정하지 못한 조문은 엔진이 판정하지 않고 표시만 하고, 스킬이 문맥을 확인해 다시 검증한다. 실측 문서 5편에서 생략 조문 24건 중 19건을 엔진이 풀었고, 손으로 한 재검증과 19건 모두 같은 판정이 나왔다.

판정은 LLM이 아니라 규칙이 내린다. LLM은 도구를 호출하고 문맥만 확인하므로, 누가 돌려도 같은 판정이 나온다.

## 판정

| 판정 | 조건 | 다음 행동 |
|---|---|---|
| **FAIL (반려)** | 없는 조문, 제목 불일치, 없는 법령, 실존할 수 없거나 선고일이 다른 판례, 폐지 법령을 현행처럼 인용, 삭제 조문, 변경된 판례 중 하나라도 있다 | 작성자에게 돌려보낸다 |
| **INCOMPLETE (검증 미완료)** | FAIL은 없고, 법제처 조회가 실패한 인용이 있다 (인증키 오류, 네트워크, 요청 상한) | 통과가 아니다. 원인을 고치고 다시 검증한다 |
| **PASS_WITH_WARNINGS (조건부 통과)** | 옛 법령명, 구법 인용, 시행 예정 개정, 미확인 판례, 원문 제목 차이 같은 경고가 있다 | 경고를 반영해야 통과한다 |
| **PASS (통과)** | 모든 인용이 확인됐고 경고가 없다 | 그대로 쓴다 |
| **NO_CITATIONS** | 검증할 인용이 없다 | 통과가 아니다 |

설계 원칙은 셋이다.

- **오탐 0이 검출률보다 먼저다.** 진짜 인용을 반려하면 아무도 게이트를 믿지 않는다. 그래서 검색되지 않는 판례는 가짜로 단정하지 않고 경고로 둔다.
- **확인하지 않은 것은 통과가 아니다.** 문맥 확인을 하나라도 남기면 PASS가 나오지 않는다. 조회가 실패하면 경고로 덮지 않고 INCOMPLETE로 멈춘다. 인증키가 없으면 판정을 내지 않고 오류로 끝난다.
- **근거는 법제처 응답 원문이다.** 요약하거나 지어낸 근거는 받지 않는다.

상태 목록 전체는 [references/verdict-rules.md](references/verdict-rules.md)에 있다.

## 설치

필요한 것은 두 가지다. **스킬**(이 저장소 자체. 루트에 `SKILL.md`가 있다)과 **MCP 서버**(`mcp/`). 서버는 내 컴퓨터에서 돌고, 인증키는 `mcp/.env`에만 둔다.

- Node.js 20.19 이상, Python 3.9 이상
- 법제처 Open API 인증키(OC). [법제처 국가법령정보 공동활용](https://open.law.go.kr/)에서 무료로 발급받는다. 아래의 `인증키`를 발급받은 값으로 바꾼다.

### Claude Code

**1. 스킬 받기**

```bash
git clone https://github.com/airoasting/korean-law.git ~/korean-law
```

```bash
ln -s ~/korean-law ~/.claude/skills/korean-law
```

**2. 서버 빌드와 인증키**

```bash
cd ~/korean-law/mcp && npm ci && npm run build
```

```bash
printf 'KOREAN_LAW_OC=인증키\nKOREAN_LAW_MAX_REQUESTS=400\n' > ~/korean-law/mcp/.env
```

**3. 서버 등록**

```bash
claude mcp add korean-law -- node ~/korean-law/mcp/build/server.js
```

**4. 확인.** Claude Code에서 `/mcp`를 열어 `korean-law`가 연결됐는지 본다. 그다음 `/korean-law`로 스킬을 부른다.

### Codex

**1. 스킬 받기**

```bash
git clone https://github.com/airoasting/korean-law.git ~/korean-law
```

```bash
ln -s ~/korean-law ~/.codex/skills/korean-law
```

**2. 서버 빌드와 인증키**

```bash
cd ~/korean-law/mcp && npm ci && npm run build
```

```bash
printf 'KOREAN_LAW_OC=인증키\nKOREAN_LAW_MAX_REQUESTS=400\n' > ~/korean-law/mcp/.env
```

**3. 서버 등록**

```bash
codex mcp add korean_law -- node ~/korean-law/mcp/build/server.js
```

또는 `~/.codex/config.toml`에 직접 적는다 (경로는 절대경로로).

```toml
[mcp_servers.korean_law]
command = "node"
args = ["/Users/내이름/korean-law/mcp/build/server.js"]
```

**4. 확인.** Codex에서 `/mcp`로 `korean_law`가 연결됐는지 본다. 그다음 "korean-law 스킬로 이 문서 인용 검증해 줘"라고 말한다.

### Claude 데스크탑 앱

데스크탑 앱은 터미널의 PATH를 모를 수 있으니 node는 절대경로로 적는다 (`which node`로 확인). 아래 경로는 `~/korean-law`에 받았다고 가정한다. `내이름`은 실제 사용자 폴더 이름으로 바꾼다. 스킬 받기와 서버 빌드·인증키는 위 Claude Code 1, 2단계와 같다.

- **Code 탭**: Claude Code 설정을 쓴다. 위 Claude Code 3단계를 그대로 하면 된다. 스킬은 `~/.claude/skills/korean-law`를 읽는다.
- **채팅 탭**: 설정 → 개발자 → 구성 편집으로 `~/Library/Application Support/Claude/claude_desktop_config.json`을 연다. 이미 있는 항목은 두고, 맨 위 단계에 `mcpServers`를 더한다.

```json
{
  "mcpServers": {
    "korean-law": {
      "command": "/usr/local/bin/node",
      "args": ["/Users/내이름/korean-law/mcp/build/server.js"]
    }
  }
}
```

앱을 완전히 종료(⌘Q)한 뒤 다시 연다. 채팅 탭에서는 스킬의 파일 절차가 보장되지 않으므로 "이 문서를 verify_document로 검증해 줘"처럼 도구를 바로 부른다. 판정과 검증표가 그대로 나온다.

### Codex 데스크탑 앱

Codex 앱은 Codex CLI와 같은 `~/.codex/config.toml`과 `~/.codex/skills/`를 읽는다. 위 Codex 1~3단계를 하면 앱에도 적용된다. 파일에 직접 적을 때도 node는 절대경로로 적는다.

```toml
[mcp_servers.korean_law]
command = "/usr/local/bin/node"
args = ["/Users/내이름/korean-law/mcp/build/server.js"]
```

앱을 다시 열고 설정의 MCP 항목에서 `korean_law`가 켜져 있는지 본다.

### MCP 없이 터미널에서

서버를 등록하지 않아도 같은 엔진으로 문서 한 편을 검증할 수 있다.

```bash
node ~/korean-law/mcp/scripts/verify-file.mjs 문서.md 2026-10-04 > evidence.json
```

두 번째 인자(기준일)는 생략하면 오늘이다.

## 사용

문서를 주고 이렇게 말한다. 두 도구 모두 같다.

```
이 의견서 법률 인용 검증해 줘: contracts/opinion.md
```

Claude Code에서는 `/korean-law`로 바로 부를 수도 있다. 행위·계약 시점이 중요한 문서는 기준일을 함께 알려 준다. 그날 시행 중이던 본문으로 대조한다.

결과는 작업 폴더의 `output/{YYYYMMDD}_NN/`에 남는다.

| 파일 | 내용 |
|---|---|
| `evidence.md` | 사람이 읽는 법률 근거 검증표 |
| `evidence.json` | 기계가 읽는 판정 (`korean-law/evidence@2` 스키마) |
| `raw/document-N.json` | `verify_document` 응답 원문 |
| `overrides.json` | 문맥 확인 결과와 근거 |

### MCP 도구

| 도구 | 하는 일 |
|---|---|
| `verify_document` | 문서 전체의 조문·판례 인용 검증, 판정 JSON과 검증표 |
| `check_precedent` | 판례 하나의 생사 확인 (후속 판결, 전원합의체 변경 문구) |
| `find_law` | 법령 검색 (약칭 가능, 시행 예정 개정 표시) |
| `read_law` | 기준일에 시행 중인 법령 본문, 조문 하나만도 가능 |
| `find_decision` | 판례·헌재 결정 검색 (사건번호 또는 키워드) |
| `read_decision` | 판례·헌재 결정 본문 |

## 평가

`evals/`에 회귀 테스트가 있다. 가짜 인용 10가지 유형(없는 조문, 제목 불일치, 미래 사건번호, 과거 연도 가짜 사건번호, 폐지 법령, 변경 판례, 옛 법령명, 삭제 조문, 없는 법령, 없는 목)과 정당한 인용 변형(표기 변형, 약칭, 헌재 결정, 구법 인용, 문서 안 약칭 정의, 시행 예정 개정, 법령명 생략, 사내 규범 조항)을 섞은 시드 27개다.

| 지표 | 결과 | 기준 |
|---|---|---|
| 진짜 인용을 FAIL로 판정 (오탐) | 0건 / 70 | 0건 |
| 정당한 인용의 기대 판정 적중 | 100% | 참고 |
| 가짜·낡은 인용 검출 | 26/26 | 90% 이상 |
| FAIL이어야 하는 유형의 FAIL 판정 | 19/19 | 100% |
| 미검출 인용 | 0건 | 0건 |
| 문서 판정 일치 | 27/27 | 전부 |
| 문서 1편 처리 | 최대 4.3초 | 60초 이내 |

시드 정답은 기준일(2026-10-04)에 묶여 있고, 회귀는 `asOf`로 그날 시행 중이던 본문을 대조해 날짜가 지나도 같은 결과를 낸다.

엔진 단위 테스트(법제처 호출 없음, 25개)는 `mcp/test/`에 있다 (`npm test`). 실행 방법과 기록은 [evals/README.md](evals/README.md)에 있다.

## 한계

- **법률 자문이 아니다.** 인용이 실존하고 현행인지만 본다. 인용이 논지를 실제로 받치는지는 판단하지 않는다.
- **법령명 추정에는 한계가 있다.** 다른 문장에 있고 제목도 없는 생략 조문은 엔진이 판정하지 않는다. 스킬의 문맥 확인이 필요하다.
- **목 단위까지 검증한다.** 목 아래 세목은 보지 않는다.
- **판례 검색 범위는 법제처 수록 판례다.** 하급심·미수록 판례는 '미확인'으로 남는다.
- **판례 생사는 후속 판결 본문의 문구로 판단한다.** 전원합의체 최대 10건과 그 밖의 후속 판결 3건의 본문을 읽는다. 문구 없이 법리만 바뀐 경우는 '불확실'로 남을 수 있다.

```

evals/               시드 27개, 채점 기록, AI 작성 문서 실측
docs/DESIGN.md       설계서와 단계별 결과
README.md · LICENSE
```
