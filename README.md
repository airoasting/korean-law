# korean-law

AI가 쓴 한국 법률 문서에서 조문과 판례 인용을 뽑아 **법제처 원문과 대조하고, 통과인지 반려인지 판정하는** 스킬이자 MCP 서버다. **Claude Code와 Codex**에서 같은 스킬 폴더, 같은 서버로 돌아간다. 도구별 설치 방법은 [아래](#설치)에 있다.

계약서 검토, 법률 의견서, 준비서면, 세무·내부통제 문서를 넣으면 **법률 근거 검증표**가 나온다. 인용마다 실제로 있는지, 지금도 유효한지, 제목과 선고일이 맞는지, 판례가 뒤집히지 않았는지를 확인한 표다. 법률 의견은 내지 않고 사실만 가린다.

## 왜 만들었나

요즘은 계약서 검토 메모나 법률 의견서 초안을 AI에게 맡기는 일이 많다. 문장만 보면 그럴듯하다. 문제는 그 안에 적힌 "○○법 제△조"나 "대법원 ○○다○○ 판결"이 정말 맞는지, 법을 모르는 사람은 확인하기 어렵다는 데 있다.

그래서 직접 시험해 봤다. AI(Claude)에게 15년 차 기업 변호사 역할을 맡겨 법무 문서 5편을 쓰게 하고, 인용 81건을 하나하나 법제처 원문과 맞춰 봤다. 그중 3건이 틀렸고, 5편 가운데 2편은 그대로 내보내면 안 되는 문서였다.

| 문서 | AI가 쓴 인용 | 실제 |
|---|---|---|
| 부당해고 준비서면 | 민사소송법 제272조(준비서면) | 제272조의 제목은 '변론의 집중과 준비'다 |
| 부당해고 준비서면 | 대법원 2003. 7. 22. 선고 2002두12052 (해고 판례로 인용) | 실제로는 2005. 1. 28.에 선고된 공정거래 사건이다 |
| 가지급금 세무 의견서 | 법인세법 시행령 제53조(업무무관 가지급금 등의 범위) | 제53조의 제목은 '업무무관자산등에 대한 지급이자의 손금불산입'이다 |

눈여겨볼 대목은 세 건 모두 **번호 자체는 실제로 있다**는 점이다. 없는 번호를 지어낸 것이 아니라, 있는 번호에 다른 내용을 붙였다. 그래서 흔히 쓰는 확인 방법으로는 걸러지지 않는다.

- **AI에게 다시 묻기**: 같은 AI가 같은 실수를 되풀이하거나, 물을 때마다 답이 바뀐다.
- **인터넷 검색**: 시간이 오래 걸리고, 찾은 내용이 지금 시행 중인 법인지 개정 전 법인지 알기 어렵다.
- **번호만 확인하기**: 위 세 건처럼 번호는 맞고 내용이 틀린 경우를 그냥 지나친다.

그래서 필요했던 것은 **법제처 원문을 기준으로, 내용까지, 늘 같은 기준으로, 몇 초 안에** 확인해 주는 도구였다. korean-law는 이를 위해 만들었다.

시험 기록 전체는 [evals/blackdocs/2026-10-04/FINDINGS.md](evals/blackdocs/2026-10-04/FINDINGS.md)에 있다.

## 무엇이 다른가

앞의 문제를 풀기 위해 다섯 가지를 갖췄다.

**1. 번호만 보지 않고 내용까지 본다.**
AI는 실제로 있는 조문 번호에 엉뚱한 제목을 붙이곤 한다. '민사소송법 제272조(준비서면)'라고 썼는데, 실제 제272조의 제목은 '변론의 집중과 준비'인 식이다. korean-law는 조문 제목과 판결 선고일까지 법제처 원문과 맞춰 본다.

**2. 지금 시행 중인 법으로 확인한다.**
법은 자주 바뀐다. 게다가 법제처의 최신 본문에는 공포만 되고 아직 시행되지 않은 개정이 섞여 있다. 이 본문과 그대로 비교하면, 아직 유효한 조문을 '없어진 조문'으로 잘못 판단할 수 있다. korean-law는 실제로 시행 중인 본문과 대조하고, 곧 바뀔 조문은 따로 알려 준다. 계약 체결일처럼 과거의 특정 날짜를 기준으로 확인할 수도 있다.

**3. AI가 아니라 정해진 규칙이 판정한다.**
AI에게 "이 인용 맞아?"라고 물으면 물을 때마다 답이 달라질 수 있다. korean-law는 정해진 규칙으로 판정하기 때문에, 같은 문서는 언제 돌려도 같은 결과가 나온다. 판정마다 법제처에서 확인한 근거가 한 줄씩 붙는다.

**4. 멀쩡한 인용을 틀렸다고 하지 않는다.**
확실하지 않으면 '틀림'이 아니라 '확인 필요'로 표시한다. 예컨대 법제처에서 찾지 못한 판례를 가짜로 단정하지 않는다. 하급심 판결은 법제처에 없을 수 있기 때문이다. 네트워크 문제 등으로 확인하지 못했을 때도 '통과'로 넘기지 않고 '확인 못 함'으로 멈춘다. 시험 문서 28편을 돌린 결과, 진짜 인용 71건 가운데 틀렸다고 판정한 것은 한 건도 없었다.

**5. 문서를 넣으면 몇 초 만에 끝난다.**
'민법 750조', '같은 법 제3조'처럼 제각각인 표기도, 법 이름을 생략한 조문도 알아서 읽어 낸다. '본 계약서 제12조' 같은 계약서 자체 조항이 법 조문이 아니라는 것도 가려낸다. 문서 한 편에 보통 몇 초면 결과표가 나온다. Claude와 Codex 어디에서든 같은 방법으로 쓸 수 있다.

## 예시

[examples/saas-contract-review/](examples/saas-contract-review/)에는 SaaS 이용계약 검토 메모를 돌린 결과가 있다. 메모에 삭제된 조문(정보통신망법 제22조), 실제 사건번호에 다른 선고일을 붙인 판례, 원문과 다른 조문 제목, 지어낸 사건번호를 심어 두었는데 네 건 모두 걸렸다. 진짜 인용 4건은 모두 통과했다.

```markdown
# 법률 근거 검증표

- 판정: **FAIL (반려)**
- 법령 인용 7건 (통과 4, 경고 1, 실패 1) · 판례 인용 2건 (통과 0, 경고 1, 실패 1)

## 반려 사유 (2)

| # | 인용 | 판정 | 근거 | 고칠 곳 |
|---|---|---|---|---|
| L6 | 정보통신망 이용촉진 및 정보보호 등에 관한 법률 제22조 | 삭제된 조문 | 제22조 삭제 <2020.2.4> | 삭제 사실을 반영해 고치거나 인용을 뺀다 |
| C1 | 2013다61381 | 사건번호는 실존하나 인용한 선고일과 다름 | 본문 선고일 20150326 ≠ 실제 20181030 (손해배상(기)) | 실제 판례를 찾아 사건번호와 선고일을 바로잡거나 인용을 뺀다 |
```

판정마다 근거가 된 법제처 응답이 한 줄씩 붙는다. 프로그램이 읽을 수 있는 `evidence.json`도 함께 나온다.

## 어떻게 작동하나

MCP 서버의 `verify_document`가 문서 한 편을 한 번에 검증한다. 문서 한 편에 수 초가 걸린다(시험 문서 28편 중 가장 오래 걸린 것이 4.3초).

| 단계 | 하는 일 |
|---|---|
| 1. 표기 통일 | `민법 750조`, `§398`, `23조 1항`, `제390조 및 제750조`, `○○법(이하 '△△법')` 같은 표기를 `<법령명> 제N조` 꼴로 맞춘다 |
| 2. 인용 추출 | 조문(항·호·목 포함)과 사건번호를 뽑는다. `같은 법`, `동법 시행령`은 같은 문단에서 앞서 나온 법령으로 풀어 읽는다. `본 계약서 제12조`, `취업규칙 제5조` 같은 문서 자체 조항은 판정에서 뺀다 |
| 3. 법령 확인 | 법제처 공식 약칭 2,542건으로 정식 명칭을 찾고, 개정 연혁에서 **기준일에 시행 중이던 버전**을 고른다. 옛 이름이나 폐지된 법령도 가려낸다 |
| 4. 조문 대조 | 기준일 본문에서 조문·항·호·목이 있는지, 삭제되지 않았는지, 인용한 제목이 맞는지 대조한다. 공포됐지만 아직 시행 전인 개정은 따로 경고한다 |
| 5. 판례 확인 | 사건번호가 실제로 있는지, 본문에 적힌 선고일이 맞는지 확인한다. 헌재 결정도 같은 방식으로 본다. 실제로 있는 판례는 후속 판결을 찾아, 전원합의체 판결문에 변경·폐기 문구가 있는지 살핀다 |
| 6. 판정 | 상태별 규칙에 따라 FAIL / INCOMPLETE / PASS_WITH_WARNINGS / PASS 중 하나를 낸다 |

법령명이 빠진 조문(`…와 시행령 제53조`, `손해액은 제14조의2로`)은 앞에 나온 법령으로 추정해 검증한다. 같은 문장에 나온 법령이면 그대로 믿고, 같은 문단에 나온 법령이면 인용한 제목이 실제 제목과 맞을 때만 믿는다. 그래도 정하지 못한 조문은 엔진이 판정하지 않고 표시만 해 두며, 스킬이 문맥을 확인한 뒤 다시 검증한다. 실측 문서 5편에서는 법령명이 빠진 조문 24건 중 19건을 엔진이 스스로 풀었고, 19건 모두 따로 재검증한 결과와 판정이 같았다.

판정은 AI가 아니라 규칙이 내린다. AI는 도구를 부르고 문맥만 확인하므로, 누가 돌려도 판정이 같다.

역할로 나누면 이렇다. **BLACK이 검증을 수행하고, 나머지 세 명이 평가한다.** BLACK은 법제처 원문과 대조해 검증표와 판정을 만든다. RED, SILVER, GOLD는 그 결과와 문서를 받아, 원문 대조로는 가릴 수 없는 부분(근거를 논지에 맞게 썼는지, 논리가 이어지는지, 받는 사람이 이 문서로 결정할 수 있는지)을 10점 만점으로 평가한다. 평가는 검증표 맨 아래에 붙고, 참고용이라 통과·반려 판정은 바꾸지 않는다.

| 역할 | 하는 일 |
|---|---|
| BLACK 수행자 | 인용을 법제처 원문과 대조해 검증표를 만들고 통과·반려를 판정한다 (korean-law 엔진과 스킬) |
| RED 이성 비평가 | 주장, 근거, 결론이 끊기지 않는가. 반대 논거를 다뤘는가 |
| SILVER 분야 전문가 | 실제로 있는 근거를 논지에 맞게 썼는가. 실무 기준에 맞고 경고를 반영했는가 |
| GOLD 실제 독자 | 이 문서를 받는 사람(임원, 의뢰인, 재판부)이 이것만 보고 결정할 수 있는가 |

점수 기준과 규칙은 [references/expert-review.md](references/expert-review.md)에 있다.

## 판정

| 판정 | 조건 | 다음 행동 |
|---|---|---|
| **FAIL (반려)** | 없는 조문, 제목 불일치, 없는 법령, 있을 수 없거나 선고일이 다른 판례, 폐지된 법령의 현행 인용, 삭제된 조문, 변경된 판례 가운데 하나라도 있다 | 작성자에게 돌려보낸다 |
| **INCOMPLETE (검증 미완료)** | FAIL은 없지만 법제처 조회에 실패한 인용이 있다(인증키 오류, 네트워크, 요청 한도 초과) | 통과로 보지 않는다. 원인을 고친 뒤 다시 검증한다 |
| **PASS_WITH_WARNINGS (조건부 통과)** | 옛 법령명, 구법 인용, 시행 예정 개정, 확인되지 않은 판례, 원문과 다른 제목 같은 경고가 있다 | 경고를 반영해야 통과한다 |
| **PASS (통과)** | 모든 인용이 확인됐고 경고도 없다 | 그대로 쓴다 |
| **NO_CITATIONS** | 검증할 인용이 없다 | 통과로 보지 않는다 |

설계 원칙은 세 가지다.

- **잘못된 반려를 막는 것이 먼저다.** 진짜 인용을 반려하면 아무도 이 관문을 믿지 않는다. 그래서 검색되지 않는 판례도 가짜로 단정하지 않고 경고로 남긴다.
- **확인하지 않은 것은 통과가 아니다.** 문맥 확인이 하나라도 남아 있으면 PASS를 주지 않는다. 조회에 실패하면 경고로 덮지 않고 INCOMPLETE로 멈추며, 인증키가 없으면 아예 판정하지 않고 오류로 끝낸다.
- **근거는 법제처 응답 원문이다.** 요약하거나 지어낸 근거는 받지 않는다.

상태 목록 전체는 [references/verdict-rules.md](references/verdict-rules.md)에 있다.

## 설치

준비물은 두 가지다. 하나는 **스킬**(이 저장소 자체로, 루트에 `SKILL.md`가 있다), 다른 하나는 **MCP 서버**(`mcp/`)다. 서버는 내 컴퓨터에서 돈다. Claude Code에서는 플러그인 하나로 둘 다 설치되고, 인증키는 플러그인 설정(macOS 키체인)에 들어간다. 저장소를 직접 받아 설치하면 인증키는 `mcp/.env`에 둔다.

- Node.js 20.19 이상, Python 3.9 이상
- 법제처 Open API 인증키(OC). [법제처 국가법령정보 공동활용](https://open.law.go.kr/)에서 무료로 발급받는다. 아래 명령의 `인증키` 자리에 발급받은 값을 넣는다.

### Claude Code 플러그인 (권장)

스킬과 MCP 서버가 함께 설치된다. 서버는 미리 묶어 둔 파일(`mcp/dist/server.mjs`)이라 빌드가 필요 없고 Node.js만 있으면 된다.

**1. 마켓플레이스 추가와 설치.** Claude Code 안에서 아래 두 줄을 차례로 입력한다.

```
/plugin marketplace add airoasting/skills
```

```
/plugin install korean-law@airoasting
```

**2. 인증키 입력.** 설치하면 설정 창이 열린다. `법제처 Open API 인증키(OC)` 칸에 발급받은 값을 넣는다. 나중에 넣거나 바꾸려면 `/plugin configure korean-law@airoasting`을 연다. 터미널에서 `claude plugin install`로 설치했다면 설정 창이 뜨지 않으므로 이 명령으로 넣는다.

**3. 확인.** Claude Code를 다시 시작하고 `/mcp`에서 `plugin:korean-law:korean-law`가 연결됐는지 본다. 연결됐으면 `/korean-law`로 스킬을 부른다.

이미 아래 방법으로 `korean-law` 서버를 등록해 두었다면 같은 도구가 두 벌 보인다. 플러그인 서버가 연결된 것을 확인한 뒤 `claude mcp remove korean-law`로 예전 등록을 지운다.

### Claude Code (저장소를 직접 받아 설치)

**1. 스킬 받기**

```bash
git clone https://github.com/airoasting/korean-law.git ~/korean-law
```

```bash
ln -s ~/korean-law ~/.claude/skills/korean-law
```

**2. 서버 빌드와 인증키 설정**

### Claude 데스크탑 앱

데스크탑 앱은 터미널의 PATH 설정을 모를 수 있으므로 node는 절대 경로로 적는다(`which node`로 확인). 아래 예시는 저장소를 `~/korean-law`에 받았다고 가정하며, `내이름`은 실제 사용자 폴더 이름으로 바꾼다. 스킬 받기와 서버 빌드·인증키 설정은 위 Claude Code의 1, 2단계와 같다.

- **Code 탭**: Claude Code 설정을 그대로 쓴다. 위 Claude Code 3단계만 하면 되고, 스킬은 `~/.claude/skills/korean-law`에서 읽는다.
- **채팅 탭**: 설정 → 개발자 → 구성 편집을 눌러 `~/Library/Application Support/Claude/claude_desktop_config.json`을 연다. 기존 항목은 그대로 두고, 맨 바깥 단계에 `mcpServers`를 추가한다.

```json
{
  "mcpServers": {
    "korean-law": {
      "command": "/usr/local/bin/node",
      "args": ["/Users/내이름/korean-law/mcp/build/server.js"]
    }
  }
}
```

앱을 완전히 종료(⌘Q)했다가 다시 연다. 채팅 탭에서는 스킬의 파일 작업이 보장되지 않으므로, "이 문서를 verify_document로 검증해 줘"처럼 도구를 직접 부른다. 그래도 판정과 검증표는 그대로 나온다.

### Codex 데스크탑 앱

Codex 앱은 Codex CLI와 같은 `~/.codex/config.toml`과 `~/.codex/skills/`를 읽는다. 따라서 위 Codex 1~3단계를 마치면 앱에도 그대로 적용된다. 파일에 직접 적을 때도 node는 절대 경로로 쓴다.

```toml
[mcp_servers.korean_law]
command = "/usr/local/bin/node"
args = ["/Users/내이름/korean-law/mcp/build/server.js"]
```

앱을 다시 연 뒤, 설정의 MCP 항목에서 `korean_law`가 켜져 있는지 확인한다.

### MCP 없이 터미널에서

서버를 등록하지 않고도 같은 엔진으로 문서 한 편을 검증할 수 있다.

node ~/korean-law/mcp/scripts/verify-file.mjs 문서.md 2026-10-04 > evidence.json
```

두 번째 인자인 기준일을 생략하면 오늘 날짜로 검증한다.

## 사용

문서를 건네며 이렇게 말하면 된다. Claude Code와 Codex 모두 같다.

```
이 의견서 법률 인용 검증해 줘: contracts/opinion.md
```

Claude Code에서는 `/korean-law`로 바로 부를 수도 있다. 행위 시점이나 계약 시점이 중요한 문서라면 기준일도 함께 알려 준다. 그러면 그날 시행 중이던 본문과 대조한다.

결과는 작업 폴더의 `output/{YYYYMMDD}_NN/`에 남는다.

| 파일 | 내용 |
|---|---|
| `evidence.md` | 사람이 읽는 법률 근거 검증표 |
| `evidence.json` | 프로그램이 읽는 판정 (`korean-law/evidence@2` 형식) |
| `raw/document-N.json` | `verify_document`의 응답 원문 |
| `overrides.json` | 문맥 확인 결과와 그 근거 |
| `expert-review.json` | 전문가 3인 평가 (검증표 맨 아래에도 붙는다) |

### MCP 도구

| 도구 | 하는 일 |
|---|---|
| `verify_document` | 문서 전체의 조문·판례 인용을 검증해 판정과 검증표를 낸다 |
| `check_precedent` | 판례 하나가 아직 유효한지 확인한다 (후속 판결, 전원합의체 변경 문구) |
| `find_law` | 법령을 검색한다 (약칭 가능, 시행 예정 개정 표시) |
| `read_law` | 기준일에 시행 중인 법령 본문을 보여 준다 (조문 하나만도 가능) |
| `find_decision` | 판례와 헌재 결정을 사건번호나 키워드로 검색한다 |
| `read_decision` | 판례와 헌재 결정 본문을 보여 준다 |

## 평가

`evals/`에는 고칠 때마다 다시 돌리는 회귀 시험이 있다. 시험 문서는 28편으로, 가짜 인용 10가지 유형(없는 조문, 제목 불일치, 미래 사건번호, 과거 연도 가짜 사건번호, 폐지 법령, 변경 판례, 옛 법령명, 삭제 조문, 없는 법령, 없는 목)과 정당한 인용의 여러 변형(표기 변형, 약칭, 헌재 결정, 구법 인용, 문서 안 약칭 정의, 시행 예정 개정, 법령명 생략, 사내 규범 조항)을 섞어 만들었다.

| 지표 | 결과 | 기준 |
|---|---|---|
| 진짜 인용을 FAIL로 판정한 건수 (오탐) | 0건 / 71건 | 0건 |
| 정당한 인용의 기대 판정 적중률 | 100% | 참고 |
| 가짜·낡은 인용 검출 | 26/26 | 90% 이상 |
| FAIL이어야 할 유형의 FAIL 판정 | 19/19 | 100% |
| 놓친 인용 | 0건 | 0건 |
| 문서 판정 일치 | 28/28 | 전부 |
| 문서 1편 처리 시간 | 최대 4.3초 | 60초 이내 |

시험 문서의 정답은 기준일(2026-10-04)에 맞춰 고정돼 있다. 회귀 시험은 `asOf`로 그날 시행 중이던 본문과 대조하므로, 날짜가 지나도 결과가 같다.

엔진 단위 테스트 25개(법제처를 부르지 않음)는 `mcp/test/`에 있다(`npm test`). 실행 방법과 기록은 [evals/README.md](evals/README.md)에 있다.

## 한계

- **법률 자문이 아니다.** 인용이 실제로 있고 지금도 유효한지만 본다. 그 인용이 주장을 제대로 뒷받침하는지는 판단하지 않는다.
- **법령명 추정에는 한계가 있다.** 다른 문장에 있으면서 제목도 없는 생략 조문은 엔진이 판정하지 않으므로, 스킬의 문맥 확인이 필요하다.
- **검증은 목 단위까지다.** 목 아래 세목은 보지 않는다.
- **판례 검색 범위는 법제처에 수록된 판례다.** 하급심이나 미수록 판례는 '미확인'으로 남는다.
- **판례가 아직 유효한지는 후속 판결문의 문구로 판단한다.** 전원합의체 판결은 최대 10건, 그 밖의 후속 판결은 3건까지 본문을 읽는다. 문구 없이 법리만 바뀐 경우는 '불확실'로 남을 수 있다.

```

.claude-plugin/      플러그인 매니페스트 (MCP 서버 등록, 인증키 설정 항목)
