# korean-law 설계서

작성 2026-10-04, 갱신 2026-10-05. 상태 **Step 2 완료** (스킬 `korean-law`, 검증 엔진 MCP 서버 `mcp/`, 시험 문서 28편, 실측 5편).

## 1. 핵심 판단

법률 문서의 인용 검증은 **의견이 아니라 사실 확인**이다. 그래서 AI의 판단에 맡기지 않고, 법제처 원문과 정해진 규칙으로 판정하는 독립 도구로 만든다.

- 인용이 실제로 있는지, 지금 유효한지, 제목과 선고일이 맞는지는 원문으로 가릴 수 있다. 사람이나 AI의 평가 점수에 섞지 않는다.
- 판정은 규칙이 내린다. 같은 문서는 누가 언제 돌려도 같은 판정이 나와야 한다.
- 이 도구는 "근거가 있는가"까지만 본다. "근거를 논지에 맞게 썼는가"는 검증표를 받은 사람이 판단한다.

## 2. 이유

| 관찰 | 근거 |
|---|---|
| AI에게 법무 문서를 맡기는 일이 늘었지만, 인용이 맞는지는 법을 모르는 사람이 확인하기 어렵다 | README '왜 만들었나' |
| 도구 없이 쓴 AI 법무 문서 5편에서 인용 81건 중 3건이 틀렸고, 3건 모두 번호는 실제로 있고 내용만 달랐다 | `evals/blackdocs/2026-10-04/FINDINGS.md` |
| AI에게 다시 묻거나 웹을 검색하는 방식은 답이 흔들리고, 지금 시행 중인 법인지 가리기 어렵다 | 같은 문서 |

## 3. 무엇 (구조)

```
문서 ─▶ verify_document (표기 통일 → 인용 추출 → 법령·판례 확인 → 판정)
          │
          ├─ 법령명을 정하지 못한 조문 ─▶ 스킬의 문맥 확인 (원문 문장을 근거로 기록)
          │
          ▼
       kl.py build ─▶ evidence.md (사람용 검증표) + evidence.json (프로그램용 판정)
          │
          ▼
       전문가 3인 평가 (RED·SILVER·GOLD, 10점 만점, 참고용) ─▶ 검증표 맨 아래
```

| 판정 | 쓰는 쪽이 할 일 |
|---|---|
| FAIL | 문서를 작성자에게 돌려보낸다. 반려 사유 표의 '고칠 곳'대로 고친 뒤 처음부터 다시 검증한다 |
| INCOMPLETE | 통과로 보지 않는다. 인증키·네트워크·요청 한도를 확인하고 다시 돌린다 |
| PASS_WITH_WARNINGS | 경고를 본문에 반영한 뒤 쓴다 |
| PASS | 그대로 쓴다. 검증표를 문서 끝에 붙여 근거로 삼을 수 있다 |

전문가 평가는 원문 대조로 가릴 수 없는 층위(근거의 논지 적합성, 논리, 결정 가능성)를 짚는 참고 의견이다. 판정을 바꾸지 않는다. 판정이 FAIL이면 RED와 SILVER는 7점을 넘기지 않는다. 다른 작성·검토 흐름에 붙일 때도 위 표대로 쓰면 된다. 검증은 문서를 내보내기 전, 사람의 검토에 앞서 돌리는 것을 기본으로 한다.

## 5. 검증 엔진 (Step 2)

### 5.1 왜 엔진을 직접 만들었나

Step 1의 실측에서 믿을 만한 검증이 되려면 다음이 필요하다는 것이 드러났다. 텍스트 결과를 LLM이 해석하는 방식으로는 여섯 가지 모두 흔들린다.

| 필요 | 이유 |
|---|---|
| 판정을 구조화된 JSON으로 낸다 | 마크다운 결과를 파싱하는 단계에서 버그가 반복해서 나왔다 |
| 문서 한 번 호출로 모든 확인을 끝낸다 | 확인을 LLM이 하나씩 부르면 문서당 수십 회 호출, 수 분이 걸리고 빠뜨린다 |
| 기준일 본문으로 대조한다 | 법제처 '현행' 본문(공포일 기준)에는 시행 전 개정이 섞여 있다. 근로기준법 제105조를 오늘 유효한데도 '삭제'로 판정하는 오탐이 실제로 나왔다 |
| 엄격한 제목 대조 | 느슨한 대조는 '임의규정과 다른 의사표시'와 '임의규정'을 같다고 본다 |
| 선고일 대조 | 실존 사건번호에 다른 선고일을 붙인 인용(다른 사건)을 실존으로 통과시키면 안 된다 |
| 판례 생사를 끝까지 본다 | 전원합의체 후속 판결을 일부만 읽으면 유효한 판례에도 '불확실' 경고가 붙어 경고가 소음이 된다 |

### 5.2 설계

- **도구 면을 좁힌다.** 검증 1개(`verify_document`), 판례 생사 1개(`check_precedent`), 조사 4개(`find_law`, `read_law`, `find_decision`, `read_decision`). 인용을 확인하고 문서를 고치는 데 필요한 만큼만 둔다.
- **기준일 버전을 고른다.** `eflaw` 연혁에서 기준일에 시행 중이던 법령일련번호(MST)를 고르고, 그 MST와 기준일(`efYd`)로 본문을 받는다. 최종 공포본과 비교해 시행 예정 개정과 시행 전 신설 조문을 경고로 알린다.
- **약칭은 법제처 공식 약칭에서 만든다.** 현행 법령 전체의 법령약칭명 2,542건을 모아 사전으로 쓴다 (`npm run aliases`로 갱신). 통칭(공정거래법, AI법 등)은 별도 소수 목록으로 둔다.
- **근거가 있을 때만 추정한다.** 법령명이 생략된 조문은 앞말이 앞 조문에 이어질 때만 앞 법령으로 본다. 같은 문장이면 믿고, 같은 문단이면 인용 제목이 실제 제목과 맞을 때만 믿는다. 나머지는 판정하지 않고 `needs_context`로 넘겨 스킬이 원문을 근거로 정한다. 계약서·약관·정관·취업규칙 같은 문서 자체 조항은 엔진이 판정에서 뺀다.
- **조회 실패를 통과로 덮지 않는다.** 인증키가 없으면 판정 없이 오류로 끝나고, 조회가 실패한 인용이 있으면 판정은 `INCOMPLETE`다.
- **판례 생사는 본문 문구로 판단한다.** 대상 판례를 인용한 후속 판결 중 전원합의체 최대 10건과 그 밖의 3건의 본문에서, 대상 사건번호 앞뒤 350자 안의 변경·폐기 문구를 찾는다.
- **요청 상한과 인증키 보호.** 도구 호출 한 번이 쓸 수 있는 법제처 요청 수를 제한하고(기본 400), 캐시 키와 응답·오류에서 인증키를 지운다.

### 5.3 남은 과제

| 과제 | 근거 |
|---|---|

## 6. 품질 기준

### 검증 자체

시험 문서에 진짜 인용과 가짜 인용을 섞는다. 가짜 유형은 10가지다 (`evals/README.md`).

| 지표 | 기준 |
|---|---|
| 진짜를 FAIL로 판정한 건수 | **0건** (잘못된 반려 하나가 도구의 신뢰를 무너뜨린다) |
| 가짜·낡은 인용 검출 (WARN 또는 FAIL) | 90% 이상 |
| FAIL이어야 하는 유형의 FAIL 판정 | 100% |
| 미검출 인용 | 0건 |
| 문서 1건 검증 시간 | 60초 이내 |

과거 연도의 그럴듯한 가짜 사건번호는 원리상 '미확인' 경고로만 잡힌다 (검색되지 않은 판례를 가짜로 단정하지 않는다). 그래서 결함이 곧 손실인 문서에서는 미확인 판례를 본문에서 빼거나 `[미확인]`으로 표기하게 하는 운영 규칙으로 막는다.

## 7. 중단 기준

- AI가 쓴 실제 법무 문서를 검증했는데 인용 오류가 0건이면, 도구를 키우지 않고 축소한다. 2026-10-04 실측에서는 넘지 않았다 (81건 중 3건 오류).
- 미확인 판례 비율이 전체 인용의 50%를 넘으면 경고가 소음이 된다. 판례 검증 정책부터 다시 설계한다.
- 진짜 인용을 FAIL로 판정하는 오탐이 나오면, 고치기 전까지 그 유형의 판정을 경고로 낮춘다. 먼저 시험 문서로 재현하고 고친다.

## 10. 열린 문제

1. **다른 문장의 제목 없는 생략 조문.** 엔진이 추정하지 않아 스킬의 문맥 확인에 기댄다. 오탐 위험 없이 더 풀 방법이 있는지 시험 문서로 먼저 잰다.
2. **문구 없이 바뀐 판례.** 후속 판결이 변경 문구 없이 법리만 바꾼 경우는 '불확실'로 남는다. 원리상 한계라 경고로 둔다.
