# korean-law 설계서 (Law Gate)

작성 2026-10-04, 갱신 2026-10-05. 상태 **Step 2 완료** (스킬 `korean-law`, 검증 엔진 MCP 서버 `mcp/`, 시드 28개, 실측 5편). 다음은 Step 3 Roasting 통합.

## 1. 핵심 판단

법률 근거 검증은 **6번째 색으로 넣지 않는다. Roasting 파이프라인 안의 게이트(계기판)로 넣는다.**

- 인용이 실존하는지는 의견이 아니라 사실이다. 비평가 네 명의 투표나 평균에 섞으면 안 된다.
- 5-Color의 정체성(5인 분리)을 흔들지 않는다. 게이트는 페르소나가 아니라 도구다.
- 게이트 결과는 SILVER(분야 전문가)가 읽는 1차 출처가 된다. SILVER는 "근거가 있는가"가 아니라 "근거를 제대로 썼는가"를 본다.

## 2. 이유 (현재 공백)

| 관찰 | 근거 |
|---|---|
| 지금 법무 케이스의 인용 검증은 "웹 검색 + `[미확인]` 표기" 수준이다 | 5color `p14 계약서 검토` Tools 절, Roasting `agents/roasting-black.md` 출처 규약 |
| 법무 영역은 대부분 9.7 합격선(결함이 곧 손실)이다 | `20260501_5Color Harness/references/legal-regulatory.md:27-35` |
| Roasting 비평가는 `tools: ["Read"]`뿐이라 스스로 법령을 조회할 수 없다 | Roasting `agents/roasting-*.md` frontmatter |
| 도구 없이 쓴 AI 법무 문서 5편에서 인용 81건 중 3건이 틀렸다 | `evals/blackdocs/2026-10-04/FINDINGS.md` |

## 3. 무엇 (구조)

```
[케이스 로드] ─ 법무 케이스면 ─▶ (A) Enrich: 관련 조문·판례 사전 수집 ─▶ BLACK 초안
                                                                          │
                                                                          ▼
                                                      (B) Law Gate: verify_document + 문맥 확인
                                                         ├─ FAIL ─▶ BLACK 반려 (비평 단계 진입 금지)
                                                         └─ PASS ─▶ evidence.md 생성
                                                                          │
                                                                          ▼
                                       RED / SILVER(evidence.md 1차 출처) / BLUE / GOLD 평가
                                                                          │
                                                                          ▼
                                                    (C) 최종 산출물 하단에 "법률 근거 검증표" 첨부
```

### (A) Enrich. BLACK 작성 전

- Roasting의 기존 `enrich:` 필드를 쓴다 (Roasting `SKILL.md:290-314`, 예시 `cases/c75.md:8-11`).
- `find_law`, `read_law`, `find_decision`로 관련 조문·판례를 모아 `[ENRICHMENT FROM /korean-law]` 블록으로 BLACK 프롬프트에 붙인다.
- 목적은 처음부터 맞는 조문을 쓰게 하는 것이다. 사후 검증보다 싸다.

### (B) Law Gate. BLACK 초안과 비평 사이 (Phase 4.5)

오케스트레이터가 실행한다. 비평가에게 MCP 권한을 주지 않는다 (비평가는 결과 파일을 `Read`로 읽는다).

| 검사 | 엔진이 하는 일 | 판정 |
|---|---|---|
| 조문 실존·제목 | 기준일 본문에서 조문·항·호를 찾고 인용 제목을 대조 | 없음, 제목 불일치 → **FAIL**. 표기만 다름 → 경고 |
| 삭제·개정 | 기준일 본문과 최종 공포본을 비교 | 삭제 시행 → **FAIL**. 시행 예정 개정·신설 → 경고 |
| 법령 이름 | 공식 약칭 사전, 연혁, 폐지 목록 | 없는 법령, 폐지 법령 현행 인용 → **FAIL**. 옛 이름, 구법 인용, 미등록 약칭 → 경고 |
| 판례 실존 | 판례·헌재 결정에서 사건번호 정확 일치, 본문의 선고일 대조 | 미래 연도, 선고일 불일치 → **FAIL**. 미검색 → `[미확인]` 경고 |
| 판례 생사 | 후속 판결 본문에서 대상 사건번호 주변의 변경·폐기 문구 | 변경 문구 → **FAIL**. 확정 못 함 → 경고 |

판정 규칙:

1. **FAIL 1건이라도 있으면 점수와 무관하게 BLACK에게 반려한다.** 반려 사유는 검증표 그대로 넘긴다.
2. 경고와 `[미확인]`은 통과시키되, SILVER 평가축에 "검증표의 경고를 반영했는가"를 추가한다.
3. 게이트 반려는 Roasting의 4라운드 상한에 포함한다. 게이트만으로 2번 연속 반려되면 사용자에게 보고하고 멈춘다.

### (C) 최종 산출물

- 문서 하단에 검증표(인용, 판정, 확인일, 출처: 법제처 국가법령정보센터)를 붙인다.
- GOLD(실제 독자)는 이 표로 문서를 믿을 근거를 얻는다. 법적 효력 판단은 국가법령정보센터 원문 확인이 필요하다는 고지를 함께 단다.

## 5. 검증 엔진 (Step 2)

### 5.1 왜 엔진을 직접 만들었나

Step 1의 실측에서 게이트가 되려면 다음이 필요하다는 것이 드러났다. 텍스트 결과를 LLM이 해석하는 방식으로는 여섯 가지 모두 흔들린다.

| 필요 | 이유 |
|---|---|
| 판정을 구조화된 JSON으로 낸다 | 마크다운 결과를 파싱하는 단계에서 버그가 반복해서 나왔다 |
| 문서 한 번 호출로 모든 확인을 끝낸다 | 확인을 LLM이 하나씩 부르면 문서당 수십 회 호출, 수 분이 걸리고 빠뜨린다 |
| 기준일 본문으로 대조한다 | 법제처 '현행' 본문(공포일 기준)에는 시행 전 개정이 섞여 있다. 근로기준법 제105조를 오늘 유효한데도 '삭제'로 판정하는 오탐이 실제로 나왔다 |
| 엄격한 제목 대조 | 느슨한 대조는 '임의규정과 다른 의사표시'와 '임의규정'을 같다고 본다 |
| 선고일 대조 | 실존 사건번호에 다른 선고일을 붙인 인용(다른 사건)을 실존으로 통과시키면 안 된다 |
| 판례 생사를 끝까지 본다 | 전원합의체 후속 판결을 일부만 읽으면 유효한 판례에도 '불확실' 경고가 붙어 경고가 소음이 된다 |

### 5.2 설계

- **도구 면을 좁힌다.** 검증 1개(`verify_document`), 판례 생사 1개(`check_precedent`), 조사 4개(`find_law`, `read_law`, `find_decision`, `read_decision`). BLACK 조사와 문서 고치기에 필요한 만큼만 둔다.
- **기준일 버전을 고른다.** `eflaw` 연혁에서 기준일에 시행 중이던 법령일련번호(MST)를 고르고, 그 MST와 기준일(`efYd`)로 본문을 받는다. 최종 공포본과 비교해 시행 예정 개정과 시행 전 신설 조문을 경고로 알린다.
- **약칭은 법제처 공식 약칭에서 만든다.** 현행 법령 전체의 법령약칭명 2,542건을 모아 사전으로 쓴다 (`npm run aliases`로 갱신). 통칭(공정거래법, AI법 등)은 별도 소수 목록으로 둔다.
- **근거가 있을 때만 추정한다.** 법령명이 생략된 조문은 앞말이 앞 조문에 이어질 때만 앞 법령으로 본다. 같은 문장이면 믿고, 같은 문단이면 인용 제목이 실제 제목과 맞을 때만 믿는다. 나머지는 판정하지 않고 `needs_context`로 넘겨 스킬이 원문을 근거로 정한다. 계약서·약관·정관·취업규칙 같은 문서 자체 조항은 엔진이 판정에서 뺀다.
- **조회 실패를 통과로 덮지 않는다.** 인증키가 없으면 판정 없이 오류로 끝나고, 조회가 실패한 인용이 있으면 판정은 `INCOMPLETE`다.
- **판례 생사는 본문 문구로 판단한다.** 대상 판례를 인용한 후속 판결 중 전원합의체 최대 10건과 그 밖의 3건의 본문에서, 대상 사건번호 앞뒤 350자 안의 변경·폐기 문구를 찾는다.
- **요청 상한과 인증키 보호.** 도구 호출 한 번이 쓸 수 있는 법제처 요청 수를 제한하고(기본 400), 캐시 키와 응답·오류에서 인증키를 지운다.

## 6. 품질 기준

### 게이트 자체

시드 세트에 진짜 인용과 가짜 인용을 섞는다. 가짜 유형은 10가지다 (`evals/README.md`).

| 지표 | 기준 |
|---|---|
| 진짜를 FAIL로 판정한 건수 | **0건** (오탐 하나가 게이트의 신뢰를 무너뜨린다) |
| 가짜·낡은 인용 검출 (WARN 또는 FAIL) | 90% 이상 |
| FAIL이어야 하는 유형의 FAIL 판정 | 100% |
| 미검출 인용 | 0건 |
| 문서 1건 검증 시간 | 60초 이내 |

과거 연도의 그럴듯한 가짜 사건번호는 원리상 '미확인' 경고로만 잡힌다 (검색되지 않은 판례를 가짜로 단정하지 않는다). 그래서 9.7 영역에서는 미확인 판례를 본문에서 빼거나 `[미확인]`으로 표기하게 하는 정책으로 막는다.

### 통합 효과 (Step 3)

법무 케이스 7개를 게이트 없이, 게이트를 붙여서 각각 돌린다.

- 최종 산출물의 인용 오류 건수 (게이트 후 0건이어야 한다)
- 라운드 수 증가폭
- SILVER 점수 변화

## 7. 중단 기준

- 법무 케이스 실제 산출물 5개를 검증했는데 인용 오류가 0건이면, 게이트는 축소한다 (Enrich만 남긴다). 2026-10-04 실측에서 넘지 않았다.
- 미확인 판례 비율이 전체 인용의 50%를 넘으면, 게이트가 소음이 된다. 판례 검증 정책부터 다시 설계한다.
- 진짜 인용의 FAIL 판정(오탐)이 해결되지 않으면 Roasting 통합(Step 3)으로 넘어가지 않는다.

## 10. 열린 문제

1. **Roasting 정본 기준**. Step 3은 Roasting 엔진 v0.4.14를 기준으로 설계했다. 통합 작업 전에 정본 소스를 하나로 확정하고 그 위에서 고친다.
2. **합격 판정 규칙 불일치**. 5-Color는 "네 점수 모두 합격선 이상", Roasting 엔진은 "평균 9.5 이상"으로 고정되어 있다 (Roasting `SKILL.md:443-445`). 9.7 법무 케이스도 엔진에서는 9.5 평균으로 판정된다. 게이트와 별개로 정리가 필요하다.
